Kubernetes, as a job shop
on a factory floor

Every Kubernetes idea is drawn here as something you could walk up to: pods are machines running a program, nodes are fenced work cells with their own controller cabinet, the scheduler is the dispatcher in the planning office, and a binding is a job card blown through a pneumatic tube to the cell. Press the buttons and watch the real operations happen, one true step at a time, from bootstrapping an empty shop to a rolling update. Turn it, zoom in, switch on See-through, open the control room to watch the messages behind each move. Then point it at your own cluster.

Bootstrapping: an empty shop comes up in order

On the floorPress Bootstrap. The floor empties and the office goes dark. The lights come up in order: the seal press first (the cluster CA; it stamps a badge for the ledger, the counter and the dispatcher), then the ledger drawers, then the counter, then the dispatcher's screen, and the tube pressurises. Each cell then powers on as its controller cabinet joins: it hands in a request, the press stamps its badge, and its lamp turns green when the cell reports Ready. Only then are the orders posted on the board, the dispatcher starts writing job cards, and the cells start pulling.

Before any of that, kubeadm init runs its certs phase: it creates the cluster CA and signs a certificate for every component (the API server, its client cert for the kubelets, the front proxy, etcd's server, peer and client certs, the service-account key pair), because nothing below can talk to anything without one. Then nothing can happen before the API server is serving, and the API server cannot serve before etcd is up: that is the order it follows. The scheduler and controllers are just clients of the API server, so they start last and can restart any time.

A node joins by starting a kubelet that registers itself with the API server: kubeadm join hands it a bootstrap token and the CA's hash, the kubelet submits a certificate signing request, the controller manager approves and signs it with the CA, and only with that certificate can it register. It is not schedulable until it is Ready, which needs a container runtime and a CNI network plugin running on it. Managed clusters (EKS, GKE, DOKS) do the office for you; the cell half is still this.

All of that is kubeadm's automation of what Kubernetes The Hard Way does by hand: an openssl CA and eight key pairs (admin, node-0, node-1, kube-proxy, kube-scheduler, kube-controller-manager, kube-api-server, service-accounts), ten years of validity, node certificates named after the host, each embedded into a kubeconfig and copied to its machine; no CSRs, no bootstrap tokens, no rotation. The service-accounts pair is the seal press's second die: the API server signs every visitor pass with it (--service-account-signing-key-file, --service-account-key-file, --service-account-issuer). One more honesty note: the order the lights come up here is dependency order, not start order. The Hard Way starts kube-apiserver, kube-controller-manager and kube-scheduler together under systemd, and the clients simply retry until the API server answers.

kubeadm init --pod-network-cidr=10.244.0.0/16   # phases: certs, kubeconfig, etcd, control-plane, ...
kubectl apply -f cni.yaml                     # nodes go Ready once this runs
kubeadm join 10.0.0.1:6443 --token ... --discovery-token-ca-cert-hash ...
kubectl get nodes --watch                      # NotReady -> Ready
kubectl apply -f app/

A Pod is a machine, and a machine holds programs

On the floorSwitch on See-through and look inside any machine: one program cartridge per container (the main one large, sidecars small), the data port on the back wall patched to the cell's switch, a laminated setup sheet clipped to the side (its header reads CONFIGMAP), a small locked tool cabinet on the floor beside it (SECRET on the door), and under the whole machine a fixture pallet with a tag (PVC and the claim's name). With Labels on, the chips name the objects: CONFIGMAP web-config, SECRET api-keys, PVC data-db-0; the machine's card lists the same three rows.

A Pod is the smallest thing Kubernetes schedules. It is one or more containers that always land on the same node, share one network namespace (one IP, one set of ports: the data port) and can share volumes (the pallet). A tiny pause container holds that namespace open while app containers come and go.

Config and secrets are not baked into the image; they are mounted in from ConfigMaps (the setup sheet) and Secrets (the lockbox), so the same image runs in every environment. A PersistentVolumeClaim gives a pod storage that outlives the container (the db machine stands on one).

kubectl describe pod web-6b8fd-xk2p9
kubectl logs web-6b8fd-xk2p9 -c nginx

A Node is a work cell with its own controller

On the floorEach cell has twelve machine bays and grows a row when it needs more; the gauge on the cabinet shows how full it is. The cabinet at the corner is the kubelet. See-through shows what is in it: the runtime drive unit and the kube-proxy switch with its patch cables to every machine's data port. Next to it the tool rack holds a crate for every image this cell has pulled, and the cell's AGV waits by the cabinet. Painted beside the cell's name are its PodCIDR (the address range its machines draw from) and the routes to the other cells' ranges; the lanes between cells carry a ROUTE stencil.

A node is a machine, virtual or real. The kubelet on it watches the API server for pods bound to it, asks the container runtime (containerd, CRI-O) to pull images and start containers, runs the probes, and reports status back. kube-proxy programs the node's networking so Service addresses reach pods.

Image pulls are the kubelet's, not the scheduler's. By default a kubelet pulls one image at a time (serializeImagePulls), from the registry the first time and from its local image cache after that, and every node does this on its own, so ten nodes pull in parallel while one node queues. Nodes have capacity, too: CPU, memory and a pod count, maxPods (The Hard Way sets 16; a cell here has twelve bays), which is the cap the cabinet's gauge shows. The scheduler only places a pod where its requests fit, which is why the gauge matters and why a full floor leaves cards Pending. The drive unit in the cabinet stands for the runtime the kubelet talks to over the CRI socket (containerd, with cgroupDriver: systemd so the kubelet and the runtime agree on who owns the cgroups).

Where a machine's address comes from. Every node is handed a slice of the cluster's pod range, its PodCIDR (The Hard Way: 10.200.0.0/16 cut into a /24 per node, 10.200.0.0/24 for node-0 and so on). The CNI plugin on the node gives each pod an address from that slice and plugs it into a bridge (The Hard Way uses the plain bridge and loopback plugins). Pods on different nodes can only talk if the host knows the way: either a route per node (The Hard Way adds a static route for each node's /24 pointing at that node, the lanes between the cells) or an overlay or routing daemon that a fuller CNI brings with it. kube-proxy handles Service addresses only: in its default iptables mode it writes rules that rewrite a Service address to one pod's address, so it is not a proxy in the data path at all; ipvs and nftables are the other modes.

kubectl get nodes -o wide
kubectl describe node node-a      # capacity, allocated, conditions, Images: (the cache)
kubectl top node                   # live usage (metrics-server)

The control plane is the planning office

On the floorThe glazed office on the mezzanine. The counter by the tube's mouth is the API server. The ledger cabinet with three drawers is etcd, one drawer per Raft member. The dispatcher's desk is the scheduler. The order board on the outside wall lists the Deployments. Nothing on the floor talks to the ledger directly; everything goes over the counter.

Everything goes through the API server: kubectl, the kubelets, the controllers. It validates requests and stores the result in etcd, the only stateful part. Nothing else talks to etcd directly.

Controllers are loops: each watches one kind of object and nudges the world toward what the object says. The Deployment controller makes ReplicaSets; the ReplicaSet controller makes Pods; the scheduler picks a node for each Pod that has none and writes nothing but spec.nodeName. None of them call each other. They all just watch and write, which is why the cluster keeps working while any one of them restarts.

One road runs the other way. For kubectl logs, exec, port-forward and node metrics the counter phones the cabinet: the API server connects to the kubelet on port 10250 over mutual TLS in the other direction, presenting its own kubelet-client certificate and checking the kubelet's serving certificate against the CA. The kubelet does not take the counter's word for it: with authorization mode Webhook and anonymous access off, it asks the API server back whether this caller is allowed (a SubjectAccessReview), which is why The Hard Way creates a ClusterRole system:kube-apiserver-to-kubelet (nodes/proxy, nodes/stats, nodes/log, nodes/spec, nodes/metrics) and binds it to the API server's user. Tap a machine and press logs with the control room open to watch the round trip.

kubectl get --raw /healthz
kubectl get events --sort-by=.lastTimestamp
kubectl get rs                      # the ReplicaSets a Deployment made

The control room: what the office actually does

On the floorPress Control room (or open the figure with ?room=1). A schematic lights up and every floor operation plays through it: the request enters the API server pipeline, is written into etcd by its Raft leader, the watch fans the event out (the tube), and the controllers, the scheduler and the bound cell's kubelet each do their one job and write back. Press Scale web ▸ 5 replicas and read it top to bottom while the cells pull. Then Break ▸ stop an etcd follower (nothing changes) and Break ▸ stop the etcd leader (an election; writes wait, then resume).

The API server is a pipeline, and nothing reaches etcd by any other door: authentication (client certificates, tokens, OIDC), authorization (RBAC), mutating admission (defaults, sidecar injection), validating admission (policies), schema validation against the OpenAPI types, then the write. Every object stored gets a new resourceVersion, and every watcher sees the changes in that order.

etcd is a Raft group, usually three members; the office here is a stacked control plane of three nodes, kubeadm init on the first and kubeadm join --control-plane on two more, each with its own etcd member, API server, scheduler and controller manager (the last two hold one leader Lease between them). One is the leader for the current term. A write is appended to the leader's log, replicated to the followers, committed once a quorum (two of three) has acknowledged it, then applied to the key-value store, which is where watches stream from. Lose a follower and nothing changes: the leader still has its quorum. Lose the leader and the followers' election timers fire, one asks for votes, the term goes up by one, and for those seconds the API server can serve reads from its watch cache but cannot commit a write; the controllers simply retry.

That is the production shape, and kubeadm's: three or five members, each listening for clients on :2379 and for its peers on :2380, both over TLS with etcd's own CA. Kubernetes The Hard Way is honest about running smaller: one etcd member on the control-plane host, reached by the API server over plain http://127.0.0.1:2379 on loopback. A quorum of one has no leader to lose and no election to run; if that member dies, the API server simply fails until it is back. The ledger on this floor has three drawers; The Hard Way's has one.

Controllers never call each other. Each keeps an informer cache fed by a watch, puts the key of anything that changed on a work queue, and reconciles: compare what the object asks for with what exists, then write the difference back through the API server. The Deployment controller writes ReplicaSets, the ReplicaSet controller writes Pods, the EndpointSlice controller writes the list of Ready pod addresses that kube-proxy turns into rules. The scheduler is the same shape with a cycle per Pending pod: filter out nodes that cannot take it (room, GPUs, cordons and taints, and for a PodGroup the gang's admission), score the rest (spread), bind by writing spec.nodeName. The kubelet on that node sees the binding, asks the container runtime to pull and start, runs the probes, and writes the status back; nothing in the control plane ever starts a container itself.

kubectl get --raw /healthz?verbose            # the API server's own checks
kubectl -v=8 scale deploy/web --replicas=5    # the request, the response, its resourceVersion
kubectl get leases -n kube-system             # controller-manager and scheduler leader election
kubectl get events --field-selector reason=Scheduled
ETCDCTL_API=3 etcdctl endpoint status --cluster -w table   # leader, term, raft index per member
ETCDCTL_API=3 etcdctl member list

Try: scale to 8, then stop the etcd leader while the ReplicaSet is still creating pods, and watch the writes queue at the API server until the new leader is elected.

kubectl apply: posting an order

On the floorPress Apply ▸ cache x2. A new line appears on the order board (cache x2, running 0), two pink crates appear in the crib, and two job cards leave the counter at once through the tube. Each lands on a cell's job board; that cell's AGV drives to the crib (no cell has seen this image yet), comes back with a crate, and the machine powers up: amber andon, then green when the readiness probe passes.

You never tell Kubernetes to start a pod. You write down what should exist (a Deployment with two replicas of redis:7) and apply it. The API server stores it; from there it is controllers all the way down: Deployment to ReplicaSet to two Pending Pods, scheduler binds each to a node, and that node's kubelet pulls the image and starts it.

This is the reason apply is idempotent: applying the same file twice changes nothing, because the floor already matches the board.

# cache.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: cache }
spec:
  replicas: 2
  selector: { matchLabels: { app: cache } }
  template:
    metadata: { labels: { app: cache } }
    spec:
      containers: [{ name: redis, image: redis:7 }]

kubectl apply -f cache.yaml
kubectl rollout status deploy/cache
kubectl delete -f cache.yaml        # and the pods go with it

Scale: change the number on the board

On the floorPress Scale web ▸ 8 replicas. The board says web x8, running 3; the ReplicaSet makes five Pending cards; the dispatcher binds all five in a moment, each to the cell with the most cpu and memory left after it (every machine states its requests, every cell its allocatable; node-c, the big one, takes more), and five capsules are in the tube at once. Then the slow part belongs to the cells: each cell pulls one image at a time, but every cell already has web:v1 on its rack, so each AGV only reaches to the rack and the machines come up in quick succession, in parallel across the three cells. Scale back to 1 and the newest machines power down, freeing their bays.

Scaling only edits spec.replicas. The ReplicaSet controller compares that number with the live pods it owns and creates or deletes the difference. Binding is cheap and fast; what takes time is each node pulling and starting, and that happens on every node independently. Which pods go first when scaling down is a rule, not chance: unscheduled ones, then not-ready ones, then the youngest.

A HorizontalPodAutoscaler is just something that edits the same number on your behalf, based on CPU or a custom metric. Node image caches are why a scale-up of a known image is seconds while the first rollout of a new one is minutes: the cache is per node, so every node pays the first pull once.

kubectl scale deploy/web --replicas=8
kubectl get pods -l app=web -o wide --watch     # Pending -> ContainerCreating -> Running, per node
kubectl describe node node-a | grep -A20 Images # what the node has cached
kubectl autoscale deploy/web --min=3 --max=10 --cpu-percent=70

Try: scale to 8, then Drain a cell and watch where the evicted cards land.

Rolling update: one in, one out, and the first pull per cell

On the floorPress Roll out ▸ web v2. The board flips to v2. One card for a v2 machine goes out before any v1 machine stops; the cell that gets it has never pulled v2, so its AGV makes the long trip to the crib, and only when the new machine's andon is green does one v1 machine power down. The next v2 card that lands on a cell that already pulled v2 comes up fast from the rack. Repeat until every web machine is v2: slow on first contact with each cell, quick after.

Changing the pod template (a new image tag) makes the Deployment create a second ReplicaSet and shift replicas from old to new under two limits: maxSurge (how many extra pods may exist) and maxUnavailable (how many may be missing). The defaults are 25% of the replicas each, surge rounded up and unavailable rounded down: at three replicas that is one up and none down, one pod at a time; scale web to eight first and the same rollout moves two up and two down at once, four pods in flight. The old ReplicaSet is kept at zero so a rollback is just the same dance in reverse. The pace of a rollout is set by the slowest kubelet pull plus the readiness probe, not by the control plane; pre-pulling an image on every node (a DaemonSet that references it) is the usual way to make the first contact free. An old pod is not cut off: the moment it is marked Terminating it leaves the Service's endpoints, then the kubelet sends SIGTERM and the container finishes the requests it already has inside terminationGracePeriodSeconds (the machine's amber andon blinks while it drains), so a rollout with maxUnavailable: 0 never drops a request that was in flight.

kubectl set image deploy/web nginx=nginx:1.28
kubectl rollout status deploy/web
kubectl rollout history deploy/web
kubectl rollout undo deploy/web      # back to the previous ReplicaSet (already cached on every node)

Try: Roll out ▸ web back to v1 to watch the undo come up fast from every rack.

Self-healing: the count is the contract

On the floorPress Break ▸ delete a web pod. The machine's andon goes off and it drains: nothing new is sent to it, the parts inside it finish, then it powers down. The ReplicaSet does not wait for that: the card is marked for deletion the moment you press, the count is wrong at once, a new card goes through the tube while the old machine is still finishing, and a replacement with a new name comes up from the cell's rack. No sparks: a delete is a SIGTERM and a grace period, not a crash. Nobody restarted anything; a new machine was set up because the count was wrong.

Pods are cattle: a deleted pod is gone, with its IP and its name. What persists is the ReplicaSet's promise of three. This is why you almost never create bare pods, and why anything that must find pods (a Service, a DNS name) looks them up by label rather than by name.

kubectl delete pod web-6b8fd-xk2p9
kubectl get pods -l app=web          # a new name appears
kubectl get events | grep -i replicaset

Crash versus not-ready: two different lamps

On the floorBreak ▸ crash a container: sparks and smoke, the andon goes red then amber, and the same machine comes back green with restarts +1 on its card. The kubelet restarted the program in place; the machine kept its name, cell and data port. Crash it again and the andon stays amber for ten seconds first, then twenty, then forty: CrashLoopBackOff, the kubelet's back-off, doubling to five minutes and forgotten after ten minutes of running. Break ▸ exceed a memory limit is the same loop with a different last state, OOMKilled (exit 137): the kernel ended the program at its limit and the kubelet restarts it with the same limit. Break ▸ fail a readiness probe: the andon goes amber, nothing restarts, and the sorting station skips that machine until it passes again.

Probes must not chain. In the demo web calls api and api calls db, but each readiness probe checks only its own program, so Break ▸ delete the db pod leaves every api and web andon green and a request sent meanwhile comes back red with a 502 from the web machine that took it: api called the db Service and found no endpoint. That is the right failure. A probe that checked db would turn the api andons amber, then the web andons, and leave nothing to answer at all, and the docs warn against it for that reason: readiness is about this pod, never about its dependencies. The StatefulSet brings db-0 back and the next request is green.

A liveness probe failing means "restart this container". A readiness probe failing means "do not send me traffic", and the Service removes the pod from its endpoints until it passes. Mixing them up is the classic mistake: a liveness probe on a slow dependency turns a brownout into a restart storm.

readinessProbe: { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 5 }
livenessProbe:  { httpGet: { path: /livez,   port: 8080 }, failureThreshold: 3 }

kubectl get pods                      # READY 0/1 but STATUS Running: readiness
kubectl get pods                      # RESTARTS climbing: liveness or a crash

GPUs: resources are real things in real cells

On the floornode-c has two hydraulic presses along its front margin (green lamps). Press Apply ▸ train x3 (1 GPU each): every train machine wears a GPU tag, the dispatcher can only send their cards to node-c, two press lamps turn amber, and the third card stays Pending with the reason on the toast. Delete train and the lamps go green again.

A pod asks for resources (requests) and the scheduler only binds it where they fit: CPU and memory on every node, and extended resources such as nvidia.com/gpu only where a device plugin has advertised them. GPUs cannot be shared or overcommitted the way CPU can, so a GPU request is all-or-nothing per device. This is why "Pending" is usually a capacity question, not a bug. Scale web to eight, apply train and spark, then cache (two cpu each), and a cache card stays Pending with the real message, 0/3 nodes are available: 3 Insufficient cpu; tap a cell to see what it has left.

resources:
  limits: { nvidia.com/gpu: 1 }          # requests == limits for extended resources

kubectl describe node node-c | grep -A3 Allocatable
kubectl get pods -l app=train            # 2 Running, 1 Pending
kubectl describe pod train-...           # 0/3 nodes are available: 3 Insufficient nvidia.com/gpu

Gang scheduling: all of us or none of us

On the floorPress Apply ▸ spark x4 (gang, Volcano). Four violet cards go Pending together, and only when the dispatcher confirms four free bays at the same moment do four capsules leave the counter at once. Each cell pulls its image at its own pace, and the machines wait with their cards up until the last one has its crate; then a klaxon and the office strobe, and all four start in sync. They run, complete (blue andon), and are not replaced, because a Job is finished work, not a standing count.

The default scheduler places pods one at a time, which is wrong for a distributed training or Spark job whose workers wait on each other: three workers placed and one Pending waste three bays forever. A gang scheduler such as Volcano (or the scheduler plugins' coscheduling) adds a PodGroup with minMember: the group is admitted only when every member can be bound, then all are bound in one go. The pulls are still each node's own.

apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata: { name: spark }
spec: { minMember: 4 }
# in the Job's pod template:
schedulerName: volcano
annotations: { scheduling.k8s.io/group-name: spark }

kubectl get podgroup spark        # Pending -> Running once all 4 fit

Services and Ingress: how a part finds a machine

On the floorPress Send a request. A part comes in at the receiving dock (shop.example.com, the roller door lifts) and rides past the directory board and the sorting station without stopping: the Ingress controller at the dock already holds the web Service's EndpointSlice and sends the part straight to one green-andon web machine, picked at random. The finished part comes back out green, and the web machine sends a part of its own to api, which sends one to db. Fail a probe first and that machine is skipped; drain everything and the dock answers 503. Only a machine calling a Service by name consults the board and has its own cabinet rewrite the address.

Pods come and go, so nothing talks to a pod's IP. A Service is a stable virtual IP and DNS name (web.default.svc) with a label selector; its endpoints are the Ready pods that match, kept current by a controller and wired into every node by kube-proxy. An Ingress (or Gateway) is the HTTP front door: hostnames and paths routed to Services, usually terminating TLS. kube-proxy's iptables rules pick an endpoint at random (a probability per rule; IPVS mode can go round robin), on the node the caller is on; an ingress controller does not use the ClusterIP at all, it watches EndpointSlices and proxies to pod IPs itself. A request is bound to one endpoint when it leaves the dock, and that pod only has to stay alive for as long as the request takes: a pod that is draining (Terminating, inside its grace period) still answers, while one that crashes or is killed mid-request gives the client a connection reset, which is why graceful shutdown and client retries matter more than any Service setting.

A Service is ClusterIP by default: reachable inside the cluster only. NodePort opens the same port (from 30000 to 32767) on every node and forwards it to the Service, which is how The Hard Way exposes its nginx with no front door at all. LoadBalancer asks a cloud integration for an external address in front of a NodePort. An Ingress is only a routing rule: it does nothing until an ingress controller is installed to read it, and The Hard Way installs none. The other ways to reach a pod from your laptop, port-forward, logs and exec, do not use the conveyor: they go through the API server to the kubelet on the pod's node (the counter phoning the cabinet, chapter 4).

kubectl get svc web                   # ClusterIP 10.96.0.12  80/TCP
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl get ingress                   # shop.example.com -> web:80
kubectl port-forward svc/web 8080:80  # try it from your laptop
kubectl expose deploy/web --type NodePort --port 80   # then curl http://<any node>:3xxxx
kubectl logs web-6b8fd-xk2p9          # API server -> kubelet :10250 -> the runtime's log
kubectl exec -it web-6b8fd-xk2p9 -- sh   # the same road, kept open

Security: badges, seals and gates

On the floorLook in the office with See-through: the seal press behind the counter is the cluster CA, and the ledger, the counter and the dispatcher each wear a badge it stamped; every capsule in the tube carries a wax seal. Each cell's cabinet wears a badge too, with an expiry, and renews it on schedule (it flashes). Press Apply ▸ NetworkPolicy: db accepts only api: a gate drops across the spur into every db machine, a part from web stops at it and comes back red, a part from api lifts the boom and passes. Break ▸ forge a request sends an unsealed capsule up the tube the wrong way: the counter's screen goes red and the card is refused before it is read. Break ▸ apply a privileged pod: the inspector at the counter raises a STOP sign. Break ▸ let node-b's kubelet certificate expire: its badge goes red, its status updates are refused, the cell's lamp goes red and its machines' andons amber; a few seconds later a renewed badge arrives and it recovers. The locked drawer beside the ledger is where Secrets live, encrypted, and the control room's log panel is the office logbook: the audit log.

Everything in the office and every cell talks mutual TLS: each side presents a certificate signed by the cluster CA, and each side checks the other's. kubeadm init makes the CA in its certs phase before anything else and signs the API server's serving certificate, its client certificates to the kubelets and to etcd, the front-proxy pair, and etcd's own server and peer certificates (the three drawers verify each other too). Those certificates live in /etc/kubernetes/pki, last a year, and kubeadm upgrade renews them; kubeadm certs check-expiration tells you when they run out, and an expired API server certificate is a full outage, which is the usual way a forgotten cluster dies.

A kubelet earns its badge: kubeadm join gives it a short-lived bootstrap token and the CA's hash (so it can trust the API server before it has anything of its own). It generates a key, submits a CertificateSigningRequest, the controller manager's csrapproving controller approves requests from the bootstrap group and its csrsigning controller signs them with the CA, and the kubelet installs the result. From then on it rotates the client certificate itself at about 80% of its lifetime through the same CSR path (auto-approved for a node renewing its own), and can do the same for its serving certificate. A node whose certificate has expired cannot report at all: the node-lifecycle controller marks it NotReady after the grace period, its pods are withdrawn from every Service, and it needs a fresh token (a new kubeadm join, or kubeadm certs renew on the control plane) to come back. On The Hard Way none of this moves: the node certificates are cut once with openssl, named after the host, embedded in a kubeconfig and copied over, good for ten years.

The badge carries a name. A kubelet's certificate is issued to system:node:node-a in the group system:nodes, and that identity is what the API server authorises, not the fact of having a certificate. With --authorization-mode=Node,RBAC the Node authorizer lets a kubelet read and write only the objects of its own node: its Node, the Pods bound to it, and the Secrets, ConfigMaps and claims those Pods mount. The NodeRestriction admission plugin closes the other side, so a kubelet cannot label another node or touch another node's pods. A stolen badge for node-b opens node-b's cell and nothing else.

Pods get a visitor pass, not a badge: a bound ServiceAccount token projected into the container, short-lived (an hour by default, refreshed by the kubelet), bound to an audience and to that pod. RBAC decides what the pass opens: Roles and ClusterRoles list verbs on resources, bindings attach them to users, groups and ServiceAccounts, and the default ServiceAccount can do almost nothing. Mount no token where none is needed (automountServiceAccountToken: false).

Between authentication and the write sits admission: mutating webhooks and policies that change the object (defaults, sidecars), then validating ones that can refuse it. Pod Security Admission is the built-in validator for pod specs: a namespace label sets a level (privileged, baseline, restricted) and a mode (enforce, audit, warn), and a Pod that asks for more than the level allows (a privileged container, host namespaces, running as root under restricted) is a 403 before anything reaches etcd. The inspector refuses the privileged card here because the demo namespace carries pod-security.kubernetes.io/enforce=restricted; The Hard Way labels no namespace and runs the API server with --allow-privileged=true (its admission plugins are NamespaceLifecycle, NodeRestriction, LimitRanger, ServiceAccount, DefaultStorageClass and ResourceQuota), so there the same card is admitted. ValidatingAdmissionPolicy adds your own rules in CEL without a webhook. Image signing is the same door: an admission policy (Sigstore's policy-controller, Kyverno's verifyImages) checks the crate's seal, the image's cosign signature against a trusted key, and refuses an unsigned or altered image; pin digests so the crate that was checked is the crate that is loaded.

Secrets are base64, not encrypted, unless you say so: an EncryptionConfiguration on the API server (aescbc, aesgcm, secretbox, or kms v2 with an external key service) makes the counter encrypt Secret values before they reach etcd, so an etcd backup or a drawer pulled out of the ledger shows ciphertext: read a Secret straight from etcd and the value starts with k8s:enc:aescbc:v1:key1 (The Hard Way's check, in the commands below; it uses aescbc with identity as the fallback for reading old values). Existing Secrets are rewritten under the new key with one kubectl replace sweep. Encryption at rest is a different thing from encryption in transit: The Hard Way's API server talks to its single etcd over plain http on loopback, and kubeadm's over TLS to three members on :2379. NetworkPolicy is the only thing on this page the control plane does not enforce: the API server stores it, and the CNI plugin's agent on each node (Calico, Cilium, Antrea; not kube-proxy, and not the default kubenet) programs it. With no policy every pod can reach every pod; a policy selects pods and lists what may come in and go out, so db accepts 5432 from api closes every other gate into db, including web's. Nothing in the control plane enforces it: a NetworkPolicy object is accepted by the API server on any cluster, and on a bridge-and-routes setup like The Hard Way's it is stored and silently does nothing. The gate on this floor only drops because the CNI is one that reads policies. The audit log is the office logbook: an audit policy on the API server records every request it decided, at the level you choose (metadata, request, request and response), to a file or a webhook, and it is where "who deleted that" is answered.

On a managed cluster (EKS, GKE, AKS, DOKS) the provider owns the office half: the CA and the control-plane certificates, etcd and its encryption keys, the API server's audit pipeline, control-plane upgrades. You still own everything the cells and jobs do: RBAC, NetworkPolicy (and a CNI that enforces it), what goes into Secrets and whether an external store or KMS backs them, image provenance and the policy that checks it, Pod Security levels per namespace, and keeping the node pools patched.

The fabric: belts, diverters and BGP

On the floorThe conveyor is a small fabric. The spine is the belt along the dock side of the floor; each row of cells is a rack, and where the row's spur leaves the spine stands a diverter, the row's top-of-rack switch: a switch arm on the belt that flicks across as a part is sent down the spur, with a route strip on its post listing the ranges it has learned from the cells on its row. The spur runs to the row's corridor, and the corridor to each cell's opening. Pick Cluster ▸ fabric: BGP: every cabinet raises a BGP flag and sends a pulse across its cell, up the corridor and the spur to the diverter, a line appears on the strip for each, and the spine gains a second belt; send a few requests and watch consecutive parts take the two belts in turn. Break ▸ cut node-b's uplink sends a red pulse: the BGP session drops and the diverter withdraws the route, its line greys and the arm no longer sends that way; restore the uplink and it is announced again. A drain changes nothing here: the node is up, its speaker keeps peering, and the DaemonSet pods still on it need the route. Cluster ▸ fabric: static routes is the Hard Way: the strip painted on, the routes stencilled in front of each fence, one belt, nothing announced. Cluster ▸ service addressing swaps the cabinet's switch plate between kube-proxy's iptables and the CNI's eBPF programs.

A pod's address comes from its node's PodCIDR, so the only networking question that matters is how every other node learns where that range lives. The Hard Way writes a route per node by hand. A real data centre uses the pattern RFC 7938 describes: each rack's top-of-rack switch and each spine switch is a BGP router in its own autonomous system, the racks peer with the spines, and a prefix learned at one top-of-rack switch reaches every other with equal-cost paths over every spine, so flows spread across the fabric (ECMP). Kubernetes joins that fabric when the CNI runs a BGP speaker on every node: Cilium's BGP control plane or Calico's BIRD peers with the top-of-rack switch, announces the node's PodCIDR, and withdraws it when the node leaves. No overlay, no encapsulation: a pod address is just another route in the fabric, and the same speaker can announce Service and LoadBalancer addresses so that traffic from outside reaches a node directly.

There is no separate control network. The pneumatic tube on this floor runs along the same spine, spurs and corridors as the belts, through the same diverters, because that is how a stock cluster is wired: the kubelet's Lease renewals and its watch on the API server, the image pulls from the registry, and the pod traffic all leave the node on the same network interface over the same routes. The separation is logical, not physical: different endpoints and ports (the API server on 6443, the kubelet on 10250, pods on whatever they serve), different certificates, and whatever NetworkPolicy and firewalls add. Two real exceptions exist: some on-premises sites put the nodes' management traffic on its own VLAN, and a managed control plane (chapter 19) reaches the nodes through a tunnel that is a network of its own. On this floor the consequence is visible: cut a cell's spur and you cut its belt and its tube at once.

On the floorPress Break ▸ cut node-b's uplink: a red cross appears on the belt and on the tube where node-b's spur leaves the corridor, and parts and job cards for that cell stop at the break. The cabinet can no longer renew its Lease; the control room's node lifecycle box counts the seconds since the last renewal. After the node-monitor grace period (40 s on the simulation clock, the real default; turn the Clock up to hurry) the node goes NotReady: its cell lamp turns red, its machines' andons go to a grey-blue Unknown, and they leave their Services. The node now carries the node.kubernetes.io/unreachable:NoExecute taint, which every pod tolerates for 300 s by default; when that runs out the taint manager evicts them, the ReplicaSets raise replacement cards for other cells, and node-b keeps its now orphaned machines running until its uplink returns, at which point the returning kubelet finds its pods deleted and tears them down. Break ▸ restore node-b's uplink before the timeout cancels all of it: the node goes Ready again and nothing moves. The flags behind the numbers: the kubelet's --node-status-update-frequency (10 s) sets the Lease cadence, the controller manager's --node-monitor-grace-period (40 s) sets how long a silence is tolerated, and the pod's tolerationSeconds for node.kubernetes.io/unreachable (300 s, added by the DefaultTolerationSeconds admission plugin) sets how long an unreachable node keeps its pods.

Overlays are the other answer: a VXLAN or Geneve tunnel between nodes carries pod traffic over whatever the underlay offers, at the cost of encapsulation and of being invisible to the fabric. Most clouds sit in between, with the provider's network handing out the routes. Either way kube-proxy is a separate concern: it rewrites Service addresses, not pod addresses, and it does it in the kernel's iptables (one chain per Service, picking an endpoint at random), in IPVS, or in nftables. A CNI like Cilium can replace it entirely with eBPF programs that rewrite the destination at the socket or on the packet, with no chains to walk; DigitalOcean Kubernetes runs that way, which you can see on any such cluster by the absence of a kube-proxy DaemonSet.

kubectl get nodes -o jsonpath='{.items[*].spec.podCIDR}'   # each node's range
cilium bgp peers                   # Cilium: the speakers and their sessions
calicoctl node status              # Calico: BIRD's BGP sessions
kubectl -n kube-system get ds kube-proxy   # absent on a kube-proxy-replacement cluster
ip route                            # on a node: one route per other node's PodCIDR
kubectl get nodes -w                # Ready -> NotReady about 40 s after the last heartbeat
kubectl describe node node-b | grep -A5 Conditions   # Ready Unknown: Kubelet stopped posting node status
kubectl get lease -n kube-node-lease               # one Lease per node, renewed every 10 s

Cluster DNS: the directory board

On the floorOn the wall beside the receiving dock hangs the directory board, headed kube-dns · 10.96.0.10: one line per Service, web.default.svc -> 10.96.0.12 -> station, and for a headless Service the pods' own addresses. It is the Service, not the thing that answers. CoreDNS itself is two ordinary pods of the coredns Deployment in kube-system, scheduled into two cells like any other machine; Cluster ▸ show system pods draws them, with a kube-system band and a COREDNS label. A machine calling another Service by name glances at the board first (a brief pause at its own door, the matching line lights); a part from the dock never does, the Ingress controller holds the endpoints itself. The CoreDNS machines keep the board current: a short update tick from one of them (round robin over the Ready ones, drawn only with system pods shown) whenever a Service changes or the board is consulted. The lookup itself is data plane: a UDP packet to the kube-dns ClusterIP through kube-proxy, so it rides the belts like any part. Press Break ▸ stop CoreDNS: both machines go down, the board goes blank with NO ANSWER, parts from the dock keep flowing (the controller needs no lookup), while a machine calling a Service by name waits at its own door; the Deployment raises two replacement cards, one per cell by its anti-affinity, the cells pull coredns, and the board lights again when the first replacement is Ready, at which point the waiting machines get their answers (one that waits longer than resolv.conf's five seconds gives up and the part comes back red). Drain a cell that holds one and it moves like any pod.

Cluster DNS is not part of the control plane and does not live in a booth; it is pods in cells. The coredns Deployment in kube-system runs two of them (with an anti-affinity that prefers two nodes) behind a Service that is still called kube-dns on a fixed ClusterIP (the tenth address of the Service range, 10.96.0.10 here), and the board on the floor is that Service: the address a part asks, not the machine that answers. The question is ordinary traffic: a UDP packet from the pod to 10.96.0.10:53, rewritten by kube-proxy (or the CNI's eBPF) to one CoreDNS pod like any other Service call, which is why DNS fails exactly like any Service with no endpoints and why NetworkPolicy must allow it. The kubelet writes every pod's resolv.conf to point at it, with the search list default.svc.cluster.local svc.cluster.local cluster.local and ndots:5, which is why a pod can say web and the resolver tries web.default.svc.cluster.local first. CoreDNS answers from the API server's Services and EndpointSlices: a normal Service resolves to its ClusterIP; a headless Service (clusterIP: None) has no station and resolves to the pod addresses themselves, one A record each, which is how a StatefulSet's members find each other by name. Names outside the cluster are forwarded upstream. Because DNS is pods, it fails like pods: when kube-dns has no endpoints, new lookups time out while connections already open carry on, so a DNS outage looks like new requests failing and old ones fine. NodeLocal DNSCache puts a cache on every node to keep the lookups off the network and survive a flap.

A service mesh: escorts and sleeves

On the floorPress Apply ▸ mesh: inject sidecars into web and api: each of those machines gets an escort cartridge (the sidecar proxy), a mesh desk opens in the office annex with its own small badge press, and a part sent from web to db or api to db travels in a translucent sleeve. Then Apply ▸ canary: 10% of web to v2: one v2 web machine comes up and the rollout pauses; send ten requests and nine go to v1 and one, on the second lane with an amber lamp, to v2. Apply ▸ remove the mesh takes the escorts away and lets the rollout finish.

A mesh is a proxy beside every pod. Istio injects Envoy, Linkerd injects its own small Rust proxy, and in both the sidecar takes over the pod's traffic in and out without the application knowing. Between two escorts the connection is the mesh's mutual TLS, with certificates the mesh control plane (istiod, or Linkerd's identity service) issues from the mesh's own CA, rotated every day or so; that CA is not the cluster CA from chapter 15, and the two are easy to confuse: one proves who a kubelet is to the API server, the other proves which pod is talking to which pod. The desk also pushes rules to every escort: retries and timeouts per route, circuit breaking that stops sending to an endpoint that keeps failing, and the weighted split in the figure, which is a VirtualService in Istio or an HTTPRoute from the Gateway API in either mesh. A Service cannot do that: kube-proxy picks endpoints with no idea of version or weight, so a canary without a mesh is only ever as fine-grained as the replica count. The escorts also see every request, so the mesh is where golden-signal observability (rate, errors, latency per route) and traces come from without touching the code.

Istio's ambient mode drops the sidecars: a per-node ztunnel carries the mutual TLS for every pod on the node and an optional waypoint proxy per namespace does the routing, which spares the per-pod memory and the restarts that injection needs. The price of any mesh is another control plane to keep healthy and a hop on every request; the Gateway API is the common language the meshes and the ingress controllers are converging on.

A managed control plane

On the floorPick Cluster ▸ managed control plane. The planning office leaves the mezzanine for the provider's building past the floor's back edge, behind a fence with their sign on it, and every cabinet gets a small relay box. The tube still runs to every cell and the cabinets still reach the counter the ordinary way (every watch, every status report); only logs on a machine, the counter calling the cabinet back, now goes through the relay the cabinet dialled out. When the figure watches a real cluster it switches to this mode by itself if it sees a konnectivity agent on every node and no control-plane pods.

On EKS, GKE, AKS or DOKS the API server, etcd, the scheduler and the controllers run in the provider's own network and you are given the counter's address and nothing else. Two things make that work. The kubelets reach the API server as before, because it has a public or peered address. The API server reaching the kubelets (chapter 4: logs, exec, port-forward, metrics) is the problem, since it cannot route into your VPC; the konnectivity service solves it the way the design doc describes: a konnectivity-agent on every node dials out to a konnectivity server beside the API server and keeps the tunnel open, and the API server sends its kubelet calls through that tunnel instead of connecting directly. That is why a managed cluster carries a DaemonSet you never created, and why kubectl logs fails first when the tunnel is unhealthy while kubectl get still works.

The split of responsibility follows the fence. The provider owns the office: the CA and its certificates, etcd and its backups and encryption keys, the audit pipeline, upgrades of the control plane. You own the cells and everything on them: node pools and their patching, the CNI and its policies, RBAC, Secrets and image provenance, Pod Security, the mesh if you run one, and the workloads. Nothing in the chapters before this changes; only the place the office stands.
